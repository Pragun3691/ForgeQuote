# ADR-0009 - Gemini extraction proposes evidence-backed fields

## Production diagnostics extension (owner approved, 2026-11-06)

The focused diagnostics authorization adds production-only ai_provider_attempt JSON events through the existing request log sink. The request logger supplies its own generated request ID, never a request header value. Each started adapter attempt emits once when it succeeds, fails, or is interrupted; duration covers the provider call and response verification. The abort listener emits immediately even when the SDK ignores its signal. Later resolution/rejection cannot emit a duplicate. Pre-validation/configuration rejection and cancellation before any call do not invent attempts.

Fields: event, requestId, attempt (1 or 2), durationMs (nonnegative integer), upstreamStatus (400-599 or null), category, providerReason, providerStatus, transportCode, deadlineExpired and cancelled. Categories are SUCCESS, INVALID_RESPONSE, PROVIDER_HTTP, NETWORK_TRANSPORT, APPLICATION_DEADLINE, CLIENT_CANCELLATION and INTERNAL_EXCEPTION. Unknown category/reason/status/transport identifiers map to OTHER. Both adapter and sink explicitly project fields; raw errors, stacks, messages, metadata, source, headers, URLs and SDK objects never enter the event. The callback and sink isolate logging exceptions from extraction behavior. No new environment flag.

cancelled means the combined abort signal was set, including deadline abort; deadlineExpired distinguishes the application's timer from client interruption. A provider HTTP 504 is PROVIDER_HTTP with upstreamStatus 504, distinct from the application's AI_TIMEOUT. Retry backoff is outside attempts: a deadline during backoff produces no fictitious extra provider event; correlate the completed attempt event with the final HTTP AI_TIMEOUT. After client disconnect there may be no HTTP finish event, but the attempt event is still emitted.

The SDK's ApiError.status and privately parsed JSON ErrorInfo reason allow HTTP 400 API_KEY_INVALID to use the existing AI_PROVIDER_ACCESS response. Source: [Google GenerateContent error format](https://ai.google.dev/gemini-api/docs/generate-content/api-errors?hl=en). Other existing public messages/statuses remain unchanged. Pre-aborted and during-retry aborts normalize to existing AI_CANCELLED/AI_TIMEOUT instead of leaking raw AbortError reasons. No additional retries or timeout/model/schema/prompt changes.

Limitations: TypeError inside the generate call remains the existing fetch/transport heuristic, not proof of a particular network fault. Known Node transport codes add bounded evidence; unknown exceptions have INTERNAL_EXCEPTION with OTHER identifiers. Provider work may continue after abort. These events diagnose future reproduction; they do not identify the already-observed production cause. No live provider or cloud verification was performed in this change.

## Provider and data policy

Use the official server-only @google/genai SDK, pinned 2.32.0; Zod 4.6.7 validates structured output. Initial model gemini-3.5-flash-lite, configurable via AI_MODEL. AI_API_KEY is read only on the server, passed explicitly to the Developer API (vertexai:false), never included in the prompt, browser configuration, logs or source control. AI_TIMEOUT_MS defaults to 20000; allowed 1000-30000. Empty optional variables use defaults; invalid model syntax/deadline disables AI without blocking manual intake. No implicit GOOGLE_API_KEY/GEMINI_API_KEY, ADC or alternate-provider fallback.

Policy checked on 2026-11-03 against [Gemini additional terms](https://ai.google.dev/gemini-api/terms), [Google APIs terms](https://developers.google.com/terms), [available regions](https://ai.google.dev/gemini-api/docs/available-regions) and [model pricing](https://ai.google.dev/gemini-api/docs/pricing#gemini-3.5-flash-lite). The local demo is restricted to synthetic nonconfidential documents with two explicit request-bound attestations (synthetic/no personal data; consent to sending to Google). The UI links terms and discloses processing before extraction. These attestations are not a classifier or proof of confidentiality. Terms require adult professional/business developer use in supported regions; India is listed. Unpaid public clients in EEA/Switzerland/UK are outside this authorization. No public deployment occurred.

Configure only an unpaid project key. The application never activates billing or buys services; a key's billing/project status cannot be inferred from the key and is an operator responsibility. There is no paid/model fallback when access/quota fails. Pricing availability is documentation evidence, not proof this project's key has quota. Model documentation lists structured-output support; actual project/model access has now been verified with synthetic inference and extraction, without inspecting billing account state.

## Untrusted structured output

The model receives a separate system instruction plus JSON-encoded untrusted source. No tools, browsing, code execution, database access, keys or internal rate catalog. Instruct it to copy raw values and verbatim quotes, identify each part by an exact source header, flag conflicts and leave absent facts missing. It must not infer manufacturing facts, rate keys, costs or prices.

One strict Zod schema defines application validation and generates the provider JSON Schema. The owner-approved live correction removes only properties.parts.maxItems from the generated provider schema: the original bound caused HTTP 400 INVALID_ARGUMENT on the existing model, while removing that single keyword succeeded. Zod max(20) remains authoritative on all returned responses; all other generated provider constraints, including evidence maxItems:3, remain. Exactly three header fields (reference/customerName/dueDate); up to 20 parts with anchor and seven fields (partNumber/description/material/grossWeightKg/requestedAnnualQty/cycleTimeMin/setupHoursPerBatch). Every field has status present/missing/ambiguous, nullable rawValue and up to three quotes. Reject extra fields (including keys/prices/confidence), wrong types, overlong strings, invalid JSON, blocked/incomplete/truncated output. Semantic inconsistencies such as present without evidence become unsupported fields. No confidence percentages.

## What verified means

Verification is conservative literal validation, not general language entailment or approval:

1. Derive independent sections from explicit numbered Part 1:/Part 2: headings, legacy Part:/Item: headings, or standalone Part number: lines. A Part Number: line inside an explicit heading is metadata of that component, never a second boundary. Bound each section at the next supported heading; RFQ headers remain before the first section. Associate through an exact unique heading/identifier line, or a complete part-number value with unique verbatim evidence verified inside one section. Return one component per source section, in source order, regardless of model ordering. Unmatched proposals become visible manual-review warnings, not form rows. Missing proposals create only that source section's missing fields. Duplicate source identifiers/numbered headings, conflicting identifiers or multiple model proposals block all automatic fields for the affected section, with warnings; never select or merge a winner. Enforce the existing 20-part limit and no cross-part inheritance.
2. Find every quote verbatim within its proper section and require a unique occurrence there. Compute zero-based UTF-16 character offsets, end exclusive, and one-based source line numbers on the server. Missing, repeated or out-of-scope evidence cannot verify a field.
3. Independently recognize the matching labeled source line. The claimed raw value must equal its complete value, and a cited quote on that line must contain it. A numeric substring such as 61 inside 610 is insufficient. Unlabeled narrative may be shown as a suggestion but cannot automatically populate the form.
4. Parse the whole numeric token, optional standard thousands grouping and supported unit. Annual count must be an integer 1-1000000000 with annual labeling. Weight kg/g, cycle minutes/seconds/hours, setup hours/minutes/seconds convert using an isolated decimal.js instance at precision 80. Accept only exact results within manual bounds and six fractional digits; never round a repeating conversion. Label/value unit disagreement is ambiguous. Dates accept valid ISO or explicit day + English named month + year; numeric date ambiguity remains manual.
5. Compare all recognized labeled values in each section independently of model claims; unequal normalized facts or unresolved duplicates are ambiguous. Revision/uncertainty markers (correction, revised, amended, instead, alternatively, actually, supersedes, not final, TBD, to be confirmed) conservatively mark the section ambiguous. Model-reported ambiguity also blocks automatic mapping. Broader semantic contradictions cannot be proven universally; estimator review remains required.

Material is displayed as customer text only. No auto-matching to internal material/machine keys. Cycle/setup times are proposals only when explicitly stated, never inferred routing. Setup requires an explicit per-batch basis; generic setup time is ambiguous. Only verified normalized values copy into the manual form through a deliberate button that discloses replacement. All rate-key selects start empty; unsupported/ambiguous/missing values remain empty. Edits reset existing manual confirmation. Save still uses unmodified T02.1 validation/transaction/idempotency; extraction itself never writes an RFQ.

## Reliability and retention

- GET /api/rfq-extraction: active estimator only; safe provider/model/configured status. available means key/configuration present, not live connectivity verified.
- POST same path: active estimator, CSRF, exact Origin, {sourceText,consent:true,syntheticOnly:true}. Maximum 12000 characters and 64 KiB JSON. Existing other body limits unchanged.
- Maximum 8192 output tokens and 65536 UTF-8 response bytes. Large multipart responses may truncate and fail visibly. Total deadline includes the one optional retry. Abort on deadline/client disconnect; SDK abort cannot guarantee cancellation of provider-side work already submitted.
- At most one retry after 250 ms for 500/502/503/504 or network TypeError; no automatic retry for quota/access/model/validation/timeout errors. Disable SDK retries/continuations. No browser background retry. Re-extraction can consume quota again; only RFQ persistence has T02.1 idempotency.
- Process-local five attempts/estimator/15 minutes and two simultaneous extractions. Both are separate from manual RFQ limits. Requires shared limits before horizontal scaling; no new distributed infrastructure.
- Errors use controlled messages/codes only, including missing config, access/model failure, quota, timeout, interrupted connection, invalid output and busy/rate limit. Existing allowlist logging excludes text, provider errors, cookies and secrets. No raw output logging.
- Obvious instruction tripwires reject selected patterns before provider contact; source remains data, no tools, strict schema/evidence checks and human review constrain the rest. This is defense in depth, not a general prompt-injection detector. Polished adversarial source facts can still deceive an estimator.
- Full source/evidence exist only in request/browser memory; no extraction database table or local recovery storage. Confirmed business values use normal T02.1 storage. Refresh/logout loses unconfirmed source/review; existing save key/body recovery remains intact. React renders text, not provider HTML.

## Live correction error classification (owner approved, 2026-11-03)

The original 400/404 conflation hid the request-schema rejection. SDK ApiError HTTP status and privately parsed JSON error metadata now select controlled errors: 400 INVALID_ARGUMENT -> AI_PROVIDER_REQUEST (app HTTP 502); 404 -> AI_MODEL_UNAVAILABLE (503, model/resource absence); 401/403 -> AI_PROVIDER_ACCESS (503); 429 -> AI_QUOTA_EXCEEDED (429). Explicit HTTP 402 or billing metadata/message on 400/403 -> AI_PROVIDER_BILLING (503); remaining 400 FAILED_PRECONDITION -> AI_PROVIDER_PRECONDITION (503). A quota response stays quota even if it mentions billing. These client statuses describe a server-to-provider integration problem, not an invalid estimator source or an expired app login. Messages are fixed, with manual continuation; no provider text/detail/key/source is returned or logged. Existing no-retry policy for these failures remains. No billing activation or automated remediation.

Regression coverage: exact provider-schema difference, real SDK request serialization, Zod/adapter rejection above 20 parts, controlled failures without retry/leakage and HTTP mapping/log redaction against disposable PostgreSQL. Existing numeric/evidence/part association, auth/consent and financial golden tests remain unchanged.
